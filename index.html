The beginning of an operating system where a model makes the apps.

Its kernel is written from nothing in Rust, for x86-64 PCs. The firmware loads it directly — there is no bootloader in between.

the idea · what it does · roadmap · how it is written · run it · source

The idea

You do not install apps. You ask for one, and a model writes it.

A small kernel that is always on does the fast, exact work: sharing the processor and the memory, keeping apps apart, talking to devices. A model does the slow, clever work: it writes the app you asked for. It is not part of the kernel; it is reached over the internet.

What the model writes is a script, plain text. It runs locked in a box, where it can ask the kernel for a few things and touch nothing else. A clumsy app — one that never ends, or eats its memory — is stopped, and the kernel carries on.

kernel                  shares the processor and the memory, talks to devices
└─ the box              WebAssembly: keeps everything inside locked in
   └─ the interpreter   understands Lua
      └─ an app         a script, plain text, written by the model

The last step is built, in its first and simplest form: an app is written on request. Type make and what you want, and the model writes the app as a script, which the kernel runs once in the box. An app that ran to its end is kept on the disk and listed on the screen, though it cannot be run again yet, and it can only show one line and print to the terminal. Under it is the ground the idea stands on, built piece by piece — each piece tested, and explained in plain words.

What it does today

  • Starts itself. The firmware loads the kernel's file, the kernel asks it for the memory map and the screen, and then tells it to step aside.
  • Owns the machine. Its own interrupt table, its own page tables, a pile of free frames, a heap, and tasks that take turns under the timer.
  • Draws everything. Letters drawn by hand as small grids of dots, a panel, a chat box to type in. The word at the top of this page is drawn with those shapes.
  • Shows its own lines. Many PCs have no serial port, so the kernel's lines cover the screen while it starts, and F1 shows them again. A failure is shown on a dark red stop screen, above the lines said before it.
  • Picks a look. Type look and pick one of four looks — Blue, Night, Paper or Contrast. The whole screen changes at once, and the look is kept on the disk.
  • Speaks to the world. Its own network driver. It is given an address, looks up a name, and fetches a page over an encrypted link — the site's certificate checked against trusted roots the kernel carries.
  • Keeps things. Its own disk driver, its own part of a divided disk, and a notebook of named things where nothing already written is ever changed.
  • Locks apps in. An app is a WebAssembly program in a box: checked against the rules before it runs, with a limit on its memory and a budget of steps. A clumsy app is stopped; the kernel carries on.
  • Understands Lua. It carries an interpreter that itself runs inside the box, and hands it a script — so a script's mistake stays locked in too.
  • Asks a model. Type ask in the chat box and one fixed question goes to a model over the encrypted link, with a key you typed that shows as stars. The real provider has answered it: in a run with a real key, the model's answer appeared in the chat box.
  • Makes an app on request. Type make and what you want, such as make a dice that rolls. The model writes a Lua script; the kernel checks it, lists it in the terminal, runs it once in the box, shows the app's line in the panel, and says in one plain sentence how the run went. In a run with a real key, an app the real model wrote appeared on the screen. An app that ran to its end is kept on the disk, and a panel near the top left lists the apps kept, five a page, the newest first, there again after a restart.

Roadmap

Five tracks

The goal of the first steps, to type a request and see an app appear, is reached. What comes next is kept as five tracks, each with what is being built now, what comes next and what comes later. Tracks can be built at the same time, each in its own copy of the code (a Git worktree), and every piece lands through a pull request that GitHub builds first.

Look

“The screen looks the way I like, and I change it by asking.”

Done
Pick the screen's colours from a list of four. The screen changes at once, and the same look comes back after a restart. setup brings back the first look.
Next
Describe a look in your own words: the model suggests one, and the kernel checks it before using it. A look holds the colours, the chat box's size and rows, and the size of the letters.
Later
Drawing: a table in your look, then charts, then free shapes, always inside their panel, in colours the model picks to fit the wish.

Apps

“I wish for an app, use it, and it is still there tomorrow.”

Done
Ask for an app: type make and what you want. The model writes a Lua script, and the kernel runs it in the box. An app that ran to its end is kept on the disk and listed in a panel.
Next
Apps that take inputs the model fills in.
Later
Apps as tools the model uses, extends or makes; names the model suggests and you can change; old versions kept; the script out of sight, and a failing app says one plain sentence.

Conversation

“I just talk; boos understands and acts.”

Now
Every line typed in the chat goes to the model, which answers in words or by using tools: making an app, running a kept one, or changing the look. Only key and setup stay with the kernel.
Later
It remembers what was said, and asks back when something is missing.

Safety

“Nothing gets in or out without my yes.”

Done
Every change goes through a pull request, and GitHub builds the kernel before it can land.
Now
Faster tests: several test machines side by side, and a change runs only the tests it needs.
Next
GitHub also boots the kernel and runs the tests that need no internet.
Later
Permissions for each app, asked once and written down. Then tools from outside services, each one only with your yes.

Real PC

“boos runs on a real PC.”

Done
The kernel writes its own lines on the screen while it starts, F1 shows them again, and a failure is shown on a stop screen, so that a PC without a serial port can show them.
Now
Start from a proper boot disk: one disk file that holds the kernel and a part of its own, first in QEMU, then in VirtualBox.
Later
A first start on a real laptop from a USB stick, reading only; a driver for a real wired network card; then installing on a disk of its own.

Where tracks wait on each other: every line to the model lands after the faster tests, because both change the same tests. A look described in words and apps as tools need Conversation's tools. Tools from outside services come only after permissions.

  4. Step 4 · Done

  5. Step 5 · Done

    A 111-byte WebAssembly app printed a line through the kernel. The sandbox checks each program and caps both its memory and the number of steps it can run.

  6. Step 6 · Done

    Draw on the screen

    Starting with the screen memory supplied by the firmware, the kernel drew rectangles, then hand-drawn letters. An app can now ask it to show a message in a panel.

How it is written

  • To be read. Plain words, small files, one topic per file, and a comment above every unusual step saying why. A device "signal" is an interrupt; a "frame" is 4096 bytes of real memory.
  • Owned. Four pieces of outside code — smoltcp for the network stack, rustls with the arithmetic crates for the encrypted link, wasmi for the box, omnilua for Lua — each one read and trialled before it came in. Everything else is written for this kernel. Building it runs no build script and uses no macro crate.
  • With notes kept true. docs/ holds what the code cannot say for itself: the order things must happen in, what was tested and what was not, and the known limits.

Run it

Windows, stable Rust, QEMU — and one script:

git clone https://github.com/borisandreipavel-a11y/boos
cd boos
.\run.bat

The README walks through the setup, and says plainly what a run does: the first build fetches the outside crates, every start reaches the internet once, and the first run makes a small disk file next to run.bat.

It runs in QEMU. It has never run on real hardware. Said plainly, because a list of what works is only half the picture — the rest of that list is in the README.
